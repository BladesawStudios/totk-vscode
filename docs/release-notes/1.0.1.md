# 5th delop these you lazy ass.
- Open `BFRES` archives as an expandable file tree. Material animations show as short YAML: colours as numbers with a `#RRGGBB` swatch beside them (or write `color: "#RRGGBB"`), animated parameters as frame tables, and parameter names read from the game's `ExternalBinaryString.bfres` where a file only holds their hashes
- Each model in a `BFRES` is a folder with one editable file per material (`Models/<model>/Materials/<material>.fmat`) for its shader parameters, so colours and numbers can be edited. Shapes and bones are listed as read-only summaries
- Particle files (`.vsetb.byml`) open like an archive: a folder per effect set and a file per emitter (`Esets/<set>/<emitter>.emitter`) holding that emitter's colours. A file like `static` has hundreds of effect sets, and the old text view only ever showed the first one
- Export files as their decompressed data (`zstd`)
- Recipes: a `.recipe.yaml` is a few variables (like `color`) and the game files to change, with steps such as `tint $color` (recolour), `replace FIND -> WITH`, `copy FILE` and `delete`. Run it from the right-click menu or **TKVSC: Run Recipe** to make a whole mod in one go, and run it again with another colour to remake it
- Recipes can tint textures (`.bntx`, each pixel keeps its brightness and the texture is encoded back in its own format), include other recipes (`include: other.recipe.yaml`, sharing their variables so one `color` drives all of them), and be previewed with **TKVSC: Preview Recipe Changes**, which lists every file, entry and value that would change and warns about patterns that match nothing or files that are missing, without writing anything
- Particle colours that a channel can only store as one number shared by red, green and blue are stored as the nearest colour it can when a recipe tints them, so white glows can be tinted too
